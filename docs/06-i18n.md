# 06 — Internationalization (i18n)

This document defines the **requirements** for internationalization. It does not prescribe a specific library — the framework-native i18n solution of the chosen stack is preferred (e.g. `next-intl` for Next.js, SvelteKit's i18n routing, `i18next` for plain React). The requirements below must hold regardless of the library.

## Non-negotiable rules

1. **No hardcoded user-facing strings.** Every string a user can see — UI labels, buttons, messages, errors, dates, numbers — comes from the i18n system.
2. **i18n is set up from the start.** A new project is not "done" if it has hardcoded strings. i18n is part of the initial scaffold, not a later refactor.
3. **Keys are stable and typed.** i18n keys are part of the public contract. Renaming a key is a breaking change and must be called out in the plan phase.

## Key conventions

- Keys are namespaced by feature/domain: `auth.login.title`, `checkout.cart.empty`, `errors.notFound`.
- Keys are defined in a single source of truth (a typed key map or generated types) so that a missing key is a compile-time error.
- Use **message keys**, not English text, as the key. `auth.login.title` is correct; `"Log in"` as a key is not.

## Locale files

- One file per locale: `messages/en.json`, `messages/fr.json`, etc.
- All locale files have the same structure. A CI check (or type generation) verifies that no locale is missing a key.
- The default locale is `en`. It is the reference; other locales must match its key set.

## Interpolation and pluralization

- Use the library's interpolation for dynamic values: `checkout.total` → `"Total: {total}"`.
- Use the library's pluralization rules, not string concatenation: `items.count` → `"{count} item"` / `"{count} items"`.
- Never build sentences by concatenating translated fragments.

## Locale detection and fallback

- The user's locale is detected from the request (Accept-Language header, cookie, or URL prefix) on the server.
- The locale is persisted (cookie or URL) so the choice survives navigation.
- A fallback chain is configured: requested locale → default locale. Missing keys fall back to `en` and are logged in development.

## Formatting

- Dates, times, numbers, and currencies use the locale-aware formatters of the platform (`Intl.DateTimeFormat`, `Intl.NumberFormat`, `Intl.RelativeTimeFormat`).
- Never hardcode date or number formats in components.

## Server and client

- Server-rendered content and client-rendered content use the same message catalog and the same locale resolution.
- The locale must be consistent between server render and client hydration to avoid hydration mismatches.

## API and error messages

- API error `code`s are stable machine-readable strings (see `docs/04-api-design.md`). The client maps them to i18n keys.
- API `message` fields are developer-facing and are never rendered directly to users.

## Testing i18n

- Tests assert on i18n keys or rendered translated output, never on hardcoded English strings.
- A test verifies that every locale file has the same key set as the default locale.
- E2E tests run in at least the default locale and one additional locale to catch missing translations.
